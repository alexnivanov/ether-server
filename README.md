# ether-server

Бэкенд **Ether** — географического IRC, где мир разбит на вложенные
административные каналы (страна → область → город → район → квартал), и
пользователь автоматически состоит сразу в нескольких. Сервер геокодит координаты
в набор **ID каналов**, держит WebSocket-соединения и рассылает сообщения
подписчикам канала.

> Язык — Go. Приложение опубликовано в App Store и Google Play: в проде живые
> аккаунты, сессии и сообщения, поэтому схема БД меняется только миграцией, а
> сервер выкатывается раньше клиента (см. «Деплой»). Общий контекст проекта
> (идея, модель каналов, контракт ID каналов) — в репозитории
> [`ether-meta`](../ether-meta/CLAUDE.md); серверные детали — в
> [`CLAUDE.md`](./CLAUDE.md).

## Запуск

Конфиг — на окружение: `config.<env>.yaml` (в git не идёт, образец —
[`config.example.yaml`](./config.example.yaml)).

| Поле | Смысл |
|---|---|
| `telegram_client_id`, `apple_client_ids`, `google_client_ids` | провайдеры входа; каждый опционален, но **хотя бы один обязателен** — иначе сервер не стартует. Незаданный провайдер отвечает на `/auth/<провайдер>` кодом `501 provider_disabled` с внятным текстом (его клиент показывает как есть), поэтому в dev можно держать только один. `telegram_client_id` — числовой client id из @BotFather; `apple_client_ids` — bundle id приложения (`net.nous.ether`); `google_client_ids` — список OAuth client id (Android/iOS/Web). Всё это **audience** токенов: подписи проверяются по публичным ключам провайдеров, никаких их секретов серверу не нужно |
| `addr` | адрес прослушивания (пусто → `:8080`) |
| `db` | путь к файлу SQLite (пусто → `ether.<env>.db`) |
| `nominatim_url` | свой инстанс Nominatim (пусто → публичный сервер OSM) |
| `fcm_project_id`, `fcm_credentials_file` | пуши (см. «Пуши»); пусто → выключены |
| `telegram_notify_token`, `telegram_notify_chat_id` | канал модерации: токен бота и chat_id канала, где он админ; пусто → уведомления выключены. Единственное место, где серверу нужен секретный токен бота |
| `sentry_dsn` | ошибки и паники в Sentry (см. «Мониторинг»); пусто → выключено |
| `client_versions` | пороги версий приложения по платформам (`ios`/`android`): `min` — ниже неё клиент показывает блокирующий экран, `latest` + `latest_since` — с какой версии и с какой даты предлагать обновиться (предложение включается **неделей позже** даты: в сторах раскатка идёт долями пользователей). Блока нет → `GET /version` всем отвечает `ok`; блок платформы можно не заводить, но если он есть — все три поля обязательны. Пропущенное или невалидное значение и `min` выше `latest` — ошибка старта с указанием платформы и поля. См. `version.go` |

```sh
cp config.example.yaml config.dev.yaml   # вписать хотя бы один провайдер входа
go run .                                 # -env dev по умолчанию
go run . -env prod                       # возьмёт config.prod.yaml
go run . -config /etc/ether/custom.yaml  # явный путь вместо -env
```

Сервер принимает WebSocket-соединения на `/ws` (`ws://localhost:8080/ws`).

## Деплой (прод)

Прод — один хост (`etherapp.ru`, SSH-алиас `ether`): статический Go-бинарник под
systemd, наружу его публикует Caddy с авто-TLS. Раскладка раздельная — бинарник
и конфиг read-only, запись только в каталог с базой (`ProtectSystem=strict` +
`ReadWritePaths=/var/lib/ether`):

| Путь | Что это |
|---|---|
| `/opt/ether/ether-server` | бинарник, read-only для сервиса (владелец `ether:ether`, `0755`) |
| `/etc/ether/config.prod.yaml` | конфиг с секретами (не в git; образец — `config.example.yaml`), передаётся флагом `-config` |
| `/var/lib/ether/ether.prod.db` (+`-wal`/`-shm`) | база SQLite; `/var/lib/ether` — `WorkingDirectory` и единственный writable-путь сервиса |
| `/etc/systemd/system/ether-server.service` | юнит; запускает бинарник под пользователем `ether`. Референс — [`deploy/ether-server.service`](./deploy/ether-server.service) |
| `/opt/ether/backup.sh` | скрипт бэкапа; ставится тем же `scripts/deploy.sh` |
| `/etc/systemd/system/ether-backup.{service,timer}` | ежедневный бэкап базы (см. «Бэкапы»). Референс — [`deploy/`](./deploy) |
| `/var/lib/ether/backups/ether-latest.db.gz` | последняя копия базы |
| `/etc/caddy/Caddyfile` | reverse-proxy + TLS на `localhost:8080`. Референс — [`deploy/Caddyfile`](./deploy/Caddyfile) |

Файлы в [`deploy/`](./deploy) — референс ручной первичной настройки (сервер
поднимали руками). systemd-юнит и Caddyfile меняются на сервере; после правок
юнита — `sudo systemctl daemon-reload`.

**Выкатка новой версии** — [`scripts/deploy.sh`](./scripts/deploy.sh): собирает
статический бинарник под Linux, льёт в `/tmp`, ставит через `sudo install` и
рестартит сервис (конфиг и базу не трогает):

```sh
SSH_HOST=ether scripts/deploy.sh
```

> **Сервер выкатывается раньше клиента.** Сборка 1.4.0 присылает токен сессии
> только заголовком `Authorization: Bearer` и ходит в `GET`/`POST /messages`;
> старый сервер этого не умеет, и приложение у людей сломается целиком.
>
> **Поддержки сборок ≤1.3.0 больше нет.** Прежние места токена (тело запроса и
> query), путь `GET /history` и кадр `publish` сняты. Такая сборка не пройдёт
> `resume` — то есть встанет на сплэше; вошедшая заново читает ленту, а на
> отправку получает `error upgrade_required` с текстом «Обнови Эфир».

**Логи**: `sudo journalctl -u ether-server -f`.
**Сброс базы**: команды в [`scripts/reset-db-prod.sh`](./scripts/reset-db-prod.sh)
(запускать руками на сервере — стирает всех пользователей, сессии и сообщения).

> **Схему БД теперь меняем только миграцией — сбрасывать прод-базу нельзя.**
> Приложение опубликовано в App Store и Google Play, в базе живые аккаунты,
> сессии и сообщения. `reset-db-prod.sh` остаётся, но только для дев-окружения:
> на проде он стирает пользователей, и восстановить их неоткуда.
>
> `CREATE TABLE IF NOT EXISTS` существующую таблицу не меняет, поэтому новая
> колонка, дописанная в `storeSchema`, на живой базе сама не появится — сервер
> запустится и будет падать на запросах. Отсюда **эволюция по номерам версий**
> (`store.go`, как `onUpgrade` у Android): номер схемы лежит в самой базе
> (`PRAGMA user_version` — поле в заголовке файла SQLite, своей таблицы не надо),
> шаги пронумерованы, каждый применяется ровно один раз и в транзакции вместе с
> повышением номера. Упавший шаг откатывается целиком, и следующий запуск
> начинает его заново.
>
> Добавляя изменение: актуальный вид — в `storeSchema` (для чистых баз), шаг — в
> `migrations` (для доживших), и **поднять `schemaVersion`** — забыть его значит
> не выполнить шаг (это ловит тест). Новые таблицы и индексы шага не требуют:
> `CREATE ... IF NOT EXISTS` срабатывает и на живой базе.
>
> Порядок в `OpenStore` не случаен: **сначала шаги, потом `storeSchema`.** Схема
> описывает конечный вид и может ссылаться на то, чего в старой базе ещё нет —
> частичный индекс `messages_client_msg_id` построен по колонке, которую
> добавляет шаг версии 1. В обратном порядке старт падает с «no such column».
>
> Откат бинарника не запрещён: база новее сервера — это WARN в лог и пропуск
> шагов, а не отказ стартовать. Обратных миграций нет, план отката — вернуть
> бинарник и схему не трогать. Перед выкаткой со схемой брать бэкап руками
> (`/opt/ether/backup.sh`), не полагаясь на ночной таймер.
>
> До релиза здесь было обратное указание: схему меняли свободно, а базу
> пересоздавали — так выкатывали переход на несколько провайдеров входа
> (аккаунт под внутренним id + таблица `identities` вместо `users.tg_id`).

### Мониторинг

`GET /api/health` отдаёт `{ok, version, db, uptime_sec}` и **503**, если база не
отвечает — то есть проверяет не только «процесс жив», но и «база читается». Его
же дёргает `scripts/deploy.sh` после рестарта и печатает ответ, так что сразу
видно, какая версия поднялась.

Внешние зависимости (Nominatim, FCM, Telegram) в health намеренно не проверяются:
их недоступность не повод перезапускать сервер, а пингер начал бы бить тревогу
из-за чужих сбоев.

**Ошибки и паники — в Sentry** (`sentry.go`, включается `sentry_dsn`). Мостик —
декоратор над slog: всё, что логируется уровнем ERROR, дополнительно уходит
событием, поэтому отдельных вызовов SDK по коду нет и невозможно «забыть один из
двух». Фингерпринт события — текст сообщения (`fcm send`, `save message`), а
переменная часть живёт в атрибутах: одна проблема остаётся одной записью, сколько
бы разных `user_id` в неё ни попало. Паники в HTTP-хендлерах перехватывает
`sentryhttp` — иначе `net/http` гасит их внутри соединения и мы бы о них не знали.

Почему Sentry, а не «ERROR в Telegram-канал»: он группирует однотипные ошибки
(канал бы завалило дублями), показывает стектрейс и знает про релизы. Канал
остаётся для продуктовых событий — жалоб, блокировок, регистраций и недельной
сводки.

В события попадает внутренний `user_id` (без него разбор невозможен), поэтому
Sentry указан в privacy policy как сторонний сервис; IP, заголовки и тела
запросов не отправляются (`SendDefaultPII` выключен).

Аптайм нужно проверять **снаружи** — скрипт на упавшем сервере промолчит.
Бесплатно подходит UptimeRobot: монитор `https://etherapp.ru/api/health` раз в 5
минут, а оповещение можно направить прямо в наш служебный канал, добавив
alert-contact типа Webhook с URL

```
https://api.telegram.org/bot<токен>/sendMessage?chat_id=<chat_id>&text=Эфир:%20*monitorFriendlyName*%20*alertTypeFriendlyName*
```

— тогда алерты приходят без участия нашего сервера, что и требуется, когда он лежит.

### Автообновления ОС

Хост — Debian 13 (trixie). Обновления ставит `unattended-upgrades`, сервисы с
обновлёнными библиотеками перезапускает `needrestart`:

```sh
sudo apt install -y unattended-upgrades needrestart
```

Поверхность у нас маленькая: бинарник статический, SQLite чистая Go
(`modernc.org/sqlite`, без cgo), TLS терминирует Caddy — тоже на Go. Системные
библиотеки под приложением почти не участвуют, поэтому автообновления закрывают
ядро, glibc, systemd, openssh и сам Caddy (он в Debian и приходит из
`trixie-security`, то есть покрыт дефолтным `Origins-Pattern` без правок).
`ether-server` в списки рестартов не попадает — проверено на живом обновлении.

> **Образ VPS отключает автообновления в трёх местах, и все три молчат.**
> Настроено 23.08.2026; на новом хосте проверять всё это заново:
>
> 1. **юниты замаскированы** симлинками на `/dev/null` — `systemctl enable`
>    проходит, а `start` отказывает с «unit apt-daily.service to trigger not
>    loaded»:
>    `systemctl show apt-daily.service -p LoadState,FragmentPath` →
>    `sudo systemctl unmask apt-daily.service apt-daily-upgrade.service`;
> 2. **таймеры выключены**: `systemctl is-enabled apt-daily.timer
>    apt-daily-upgrade.timer` → `sudo systemctl enable --now …`;
> 3. **главный рубильник** `APT::Periodic::Enable "0"` в
>    `/etc/apt/apt.conf.d/10periodic` — `apt.systemd.daily` смотрит на него
>    первым и выходит, не глядя на остальные ключи. Переопределяется нашим
>    `20auto-upgrades` (читается позже, лексический порядок в `apt.conf.d`):
>    `Enable`, `Update-Package-Lists`, `Unattended-Upgrade` = 1,
>    `AutocleanInterval` = 7. Проверка — `apt-config dump | grep -i periodic`.
>
> Побочный эффект третьего пункта: индексы пакетов не освежались с создания
> хоста, из-за чего любая установка падала с 404 на файл, уже вычищенный из пула.
> Плюс в `sources.list` стоял `httpredir.debian.org` — редиректор, выведенный из
> эксплуатации в 2016-м; заменён на `https://deb.debian.org`.

`needrestart` переведён в неинтерактивный режим — иначе ночной запуск упирается в
приглашение «[Return]»: `/etc/needrestart/conf.d/50-auto.conf` со строкой
`$nrconf{restart} = 'a';` (drop-in, чтобы не спорить с пакетным файлом при его
обновлении). **Следствие:** ручной `apt upgrade` теперь тоже молча рестартует
`ether-server` и `caddy`, если обновились их зависимости — делать это лучше не в
час пик, WS-соединения оборвутся (клиенты переподключаются сами).

Ядро needrestart не умеет по определению, тут нужен ребут. Автоматический
включается в `50unattended-upgrades`:

```
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-WithUsers "false";
Unattended-Upgrade::Automatic-Reboot-Time "04:30";
```

**Но только после двух условий**, иначе ставка на «хост вернётся» ничем не
подстрахована: `systemctl is-enabled ether-server caddy ether-backup.timer` —
сервер поднимали руками, и юнит в состоянии `start` без `enable` превратит первый
же ночной ребут в бессрочный простой; и внешний пингер (см. «Мониторинг») —
без него неудачный ребут узнаётся от пользователей.

Что оно вообще работает, видно только по логу, и не в день настройки, а через
несколько суток:

```sh
sudo tail -20 /var/log/unattended-upgrades/unattended-upgrades.log
```

Пустой лог — признак, что сломан один из трёх пунктов выше, а не что обновлений
не было.

### Бэкапы

[`scripts/backup.sh`](./scripts/backup.sh) снимает копию базы и кладёт её в
`/var/lib/ether/backups/ether-latest.db.gz`. Локально хранится **только
последняя** копия (база маленькая), а история версий живёт в R2 — см. ниже.

Копия делается через `VACUUM INTO`, а не `cp`: база в WAL-режиме, и простое
копирование файла при активной записи даёт битый снимок. Пишем во временный
каталог и переносим одним `mv` — на диске никогда не лежит недописанный файл,
выглядящий как рабочая копия.

Расписание — systemd-таймер (`deploy/ether-backup.{service,timer}`), ежедневно в
04:17. Почему таймер, а не cron: у cron вывод уходит письмом root'у, а почты на
сервере нет (порт 25 закрыт) — то есть сбой бэкапа остался бы незамеченным. У
таймера вывод в journald, плюс `Persistent=true` догоняет пропущенный запуск
после простоя и не даёт запуститься двум копиям одновременно.

Установка — **один раз, с локальной машины** (на сервере репозитория нет, юниты
лежат здесь, в `deploy/`). Порядок важен: сначала на сервер попадает сам скрипт,
иначе юнит запустится в пустоту.

```sh
SSH_HOST=ether scripts/deploy.sh          # ставит /opt/ether/backup.sh
scp deploy/ether-backup.service deploy/ether-backup.timer ether:/tmp/
ssh ether 'sudo install -o root -g root -m 0644 \
    /tmp/ether-backup.service /tmp/ether-backup.timer /etc/systemd/system/ &&
  sudo systemctl daemon-reload &&
  sudo systemctl enable --now ether-backup.timer &&
  sudo systemctl start ether-backup.service'   # прогнать сразу, не дожидаясь ночи
```

Скрипт едет на сервер вместе с бинарником (`scripts/deploy.sh` ставит его в
`/opt/ether/backup.sh`), поэтому версия на сервере не разъезжается с
репозиторием. Юниты меняются редко — их достаточно скопировать один раз, а после
правок повторить `scp` + `daemon-reload`.

Проверка и диагностика:

```sh
systemctl list-timers ether-backup.timer   # когда был и будет запуск
journalctl -u ether-backup -n 20           # что сказал последний прогон
ls -lh /var/lib/ether/backups/
```

Сбои (нет базы, нет места, не прошла выгрузка) уходят сообщением в служебный
Telegram-канал — токен и `chat_id` скрипт берёт из `config.prod.yaml`, отдельных
секретов не требует. Порог свободного места — 15%.

#### Выгрузка за пределы сервера

Локальная копия лежит на **том же диске**, что и база, — она спасает от «уронил
таблицу», но не от потери сервера. Поэтому копия дополнительно уезжает в удалённое
хранилище.

Куда именно — скрипт не знает: адрес в `BACKUP_REMOTE`, сам remote описан
переменными `RCLONE_CONFIG_*` в `/etc/ether/backup.env` (root, `0600`; образец —
[`deploy/backup.env.example`](./deploy/backup.env.example)). Смена провайдера =
правка этого файла. Отдельным файлом, а не в `config.prod.yaml`: Go-серверу
доступы к хранилищу ни к чему.

Что выбрать. **Яндекс.Диск** — 5 ГБ, карта не нужна, WebDAV из коробки, российская
юрисдикция (в privacy у нас заявлен 152-ФЗ, и бэкап за рубеж — та же плоскость);
пароль берётся не основной, а «пароль приложения». **Cloudflare R2** технически
приятнее (10 ГБ, S3), но требует привязки карты даже на бесплатном тарифе — на
этом мы и споткнулись. Любое S3-совместимое (B2, Yandex Object Storage, MinIO)
подключается тем же блоком, меняется endpoint.

**Копия шифруется до отправки — `age` на публичный ключ.** На сервере лежит
только публичный, закрытый — в менеджере паролей. Это важнее, чем кажется:
получивший доступ к серверу не прочитает ни новые копии, ни те, что уже лежат в
хранилище, а провайдер видит только шифротекст. Без `AGE_RECIPIENT` скрипт не
выгружает **вовсе** и говорит об этом алертом: молча отправить персональные данные
в открытом виде хуже, чем не отправить.

**Вместе с базой уезжает конфиг** — `ether-config-latest.tar.age` и версия с
датой: `config.prod.yaml`, `backup.env` и service-account FCM. Без него
восстановленная база не поднимется, а собирать заново по консолям (перевыпустить
токен бота, скачать ключ Firebase, найти DSN Sentry) — час работы в худший для
этого момент. В локальную нешифрованную копию секреты не попадают.

Ловушка, которую стоит помнить: в `backup.env` лежат доступы к самому хранилищу, и
чтобы скачать копию, они нужны **до** неё. Поэтому доступы и закрытый ключ `age`
обязаны лежать в менеджере паролей — бэкап их не заменяет.

Заливаются два объекта: `ether-latest.db.gz.age` (перезаписывается) и
`ether-YYYY-MM-DD.db.gz.age` (история). История — не роскошь: если база
повредилась, а бэкап её исправно скопировал, «последняя копия» бесполезна. Старое
скрипт **не удаляет** — чистка средствами хранилища или руками, чтобы сбой скрипта
не мог стереть архив.

Установка на сервере:

```sh
SSH_HOST=ether scripts/deploy.sh                 # свежий backup.sh на сервер
ssh ether 'sudo apt install -y age rclone'
scp deploy/backup.env.example ether:/tmp/
ssh ether 'sudo install -m 600 -o root -g root /tmp/backup.env.example /etc/ether/backup.env'
ssh ether 'sudo nano /etc/ether/backup.env'      # хранилище + AGE_RECIPIENT
ssh ether 'sudo systemctl start ether-backup.service && journalctl -u ether-backup -n 25 --no-pager'
```

Ключи `age` генерируются **на своей машине**, не на сервере:

```sh
age-keygen -o ether-backup.key        # закрытый ключ → в менеджер паролей
grep 'public key' ether-backup.key    # публичный (age1...) → в backup.env
```

Прежний путь — `SEND_TO_TELEGRAM=1` (копия документом в служебный канал) — остался
и по умолчанию выключен: там копия уходит **без шифрования**. Годится как быстрый
костыль, но удалённое хранилище предпочтительнее.

**Восстановление из хранилища:**

```sh
# те же RCLONE_CONFIG_* и BACKUP_REMOTE, что на сервере (из менеджера паролей)
rclone ls YD:ether-backups
rclone copyto YD:ether-backups/ether-latest.db.gz.age ./backup.db.gz.age
age -d -i ether-backup.key backup.db.gz.age | gunzip > restore.db
sqlite3 restore.db 'pragma integrity_check;'    # ждём ok

# конфиг, если поднимаем сервер с нуля
rclone copyto YD:ether-backups/ether-config-latest.tar.age ./config.tar.age
age -d -i ether-backup.key config.tar.age > config.tar && tar -tf config.tar
```

дальше — как при локальном восстановлении (ниже).

**Восстановление:**

```sh
sudo systemctl stop ether-server
sudo gunzip -c /var/lib/ether/backups/ether-latest.db.gz > /tmp/restore.db
sudo sqlite3 /tmp/restore.db 'pragma integrity_check;'      # ждём ok
sudo install -o ether -g ether -m 0644 /tmp/restore.db /var/lib/ether/ether.prod.db
sudo rm -f /var/lib/ether/ether.prod.db-wal /var/lib/ether/ether.prod.db-shm
sudo systemctl start ether-server
```

Файлы `-wal`/`-shm` удаляем: они относятся к прежней базе, и рядом с
восстановленной приведут к рассогласованию.

## Как это работает

Клиент шлёт серверу **координаты**, сервер через геокодинг вычисляет набор ID
каналов для точки, подписывает соединение на них и рассылает сообщения. Два
клиента в одном месте получают одинаковые ID → попадают в один чат.

Компоненты:

| Файл | Роль |
|---|---|
| `main.go` | точка входа: флаги `-env`/`-config`, WebSocket-эндпоинт `/ws`, поднятие хаба |
| `config.go` | `Config` — конфиг окружения (`config.<env>.yaml`) |
| `store.go` | `Store` — персистентность в SQLite: аккаунты (внутренний id), способы входа (`identities`), сессии, сообщения каналов |
| `hub.go` | `Hub` — владеет подписками `channelID → клиенты`, рассылает сообщения; всё состояние меняется из одной горутины (без блокировок) |
| `client.go` | `Client` — одно соединение; `readPump` читает кадры, `writePump` — единственный писатель в сокет |
| `geocode.go` | интерфейс `Geocoder` (координаты → каналы), тип `Channel`, `StubGeocoder` для офлайн-прогонов |
| `nominatim.go` | `NominatimGeocoder` — реальный геокодинг через Nominatim (reverse + details, слоты по `rank_address`) |
| `unit_title.go` | подпись канала: тип самой единицы («Деревня», «Муниципальный округ») из данных OSM, а не имя слота |
| `geocache.go` | кеш геокодинга: клетки ~100 м, TTL сутки, склейка одновременных запросов |
| `oidc.go` | вход через Telegram / Apple / Google: проверка ID-token по публичным ключам провайдера (JWKS), секретов провайдеров не нужно |
| `rest.go` | REST-эндпоинты (вход, сессии, профиль, удаление аккаунта, чтение и отправка сообщений, голоса, жалобы, блокировки, регистрация пушей, версия клиента) |
| `publish.go` | что значит «опубликовать»: бан, лимит частоты, запись, рассылка, пуши — отдельно от разбора HTTP |
| `version.go` | `GET /version` — пора ли обновлять приложение (пороги из `client_versions`) |
| `push.go` | `Pusher` — пуши о новых сообщениях через FCM, адресно по токенам устройств (см. «Пуши») |
| `notify.go` | `Notifier` — служебные уведомления в Telegram-канал модерации (жалобы, блокировки, регистрации) |
| `admin.go` | `AdminBot` — команды модерации из служебного канала (`/ban`, `/del`, …), long-poll `getUpdates` |
| `stats.go` | еженедельная сводка в служебный канал: приходы, сообщения, заходы по ссылке установки, пробелы словаря подписей |
| `country_name.go` | русские названия стран (ISO 3166-1) для сводки |
| `sentry.go` | ошибки и паники в Sentry: декоратор slog (ERROR → событие) + перехват паник в HTTP |
| `ratelimit.go` | `RateLimiter` — частота публикаций, токен-бакет на аккаунт; тир по возрасту аккаунта (свежим уже) и по репутации |
| `cleanup.go` | фоновая уборка: сообщения живут `messageTTL` (7 дней) |
| `protocol.go` | wire-протокол: `Envelope` и типы сообщений |
| `logging.go` | `slog`-хендлер: компонент в логе выводится из имени файла |

### Кеш геокодинга

Публичный Nominatim ограничен 1 req/s, а наш геокодер сериализует запросы, поэтому
один `locate` (два запроса: `/reverse` + `/details`) занимает ~2.2 с монопольно.
Упирались бы мы не в суточную квоту, а в **задержку**: пять одновременных `locate`
дают последнему ~11 секунд, и экран «Определяем каналы…» выглядит зависшим.

`geocache.go` — декоратор над `Geocoder`:

- **ключ — координаты, округлённые до 3 знаков** (сетка ~111 м по широте, ~60–110 м
  по долготе). Проверено на ориентирах: округление не меняет набор каналов;
  экономит он **повторные** обращения к тем же клеткам — открытия приложения из
  дома и с работы, возвраты из фона, толпу в одном дворе. Едущий пользователь
  выгоды не получает: клиент шлёт `locate` при сдвиге ≥200 м, то есть каждый раз
  в новую клетку. Если движущиеся станут заметной долей — поднимать порог сдвига
  или интервал опроса на клиенте, кеш тут не поможет;
- **геокодятся сами округлённые координаты**, а не координаты того, кто первым попал
  в клетку — иначе ответ для клетки зависел бы от порядка обращений (точка у края
  могла бы «застолбить» соседний район);
- **склейка одновременных запросов** (single-flight): десять человек в одном дворе
  дают один геокодинг, а не десять в очереди по 2.2 с;
- **ошибки не кешируются** — сетевой сбой иначе отравил бы клетку на сутки;
- TTL сутки, потолок 20 тысяч клеток, вытеснение просроченных и самых старых;
- раз в час в лог идёт `geocode cache hits=… misses=… hit_rate_pct=… size=…` — по
  этой строке и решать, нужен ли свой Nominatim.

Кеш в памяти: после рестарта он холодный. Если это станет заметно (деплой в
вечерний час), следующий шаг — хранить клетки в SQLite, декоратор для этого уже
изолирован.

## Wire-протокол

Каждый WebSocket-кадр — это `Envelope`: тег типа + сырой payload (полный контракт
— в [`ether-meta/PROTOCOL.md`](../ether-meta/PROTOCOL.md)).

```json
{ "type": "locate", "data": { "lat": 55.76, "lng": 37.61 } }
```

На WebSocket остались только кадры, которым нужен живой сокет; вход, сессии,
история и всё остальное — REST (`rest.go`, таблица эндпоинтов в `PROTOCOL.md`).
Сокет авторизуется единственным способом — токеном сессии в `?token=` при
апгрейде, логин-кадров на WS нет.

| Тип | Направление | Payload |
|---|---|---|
| `locate` | client → server | `{lat, lng}` — подписывает соединение на каналы точки |
| `located` | server → client | `{channels: [...]}` |
| `message` | server → client | `{id, channel, sender_id, sender, username, avatar_url, text, ts, rating, my_vote}` |
| `removed` | server → client | `{message_id}` или `{user_id}` — контент убрали, вычистить из ленты |
| `error` | server → client | `{code, message}` |

`Channel` — `{id, level, label, name, subscribers}`, где `id` — стабильный ключ
(`RU`, `RU-MOW`, `relation/2555133`), `level` ∈ `planet | country | region | city |
district | quarter`. **Планета** (`EARTH`) — глобальный канал: есть у всех, из
координат не выводится, добавляется первой константой `PlanetChannel`.

`label` — не имя слота, а тип самой единицы («Деревня», «Муниципальный округ»):
слот про охват, подпись про объект, и в сельской местности они расходятся. Как
слово выводится из данных OSM — `unit_title.go`. `subscribers` заполняет не
геокодер, а `locate` уже после кеша: счётчик живой, в кеше он заморозился бы на
сутки.

**Сокет пингует сервер** (`client.go`): `ping` раз в 50 с, ответа ждём 60 с. В
протоколе тишина — норма (человек читает, писать нечего), а оператор или NAT
роняет простаивающий TCP через ~30–120 с, и без пингов этого не замечает ни одна
сторона: сокет становится зомби — рассылка уходит в никуда, ошибки нет. Пинг и
держит канал живым, и превращает мёртвое соединение в честный обрыв, на который у
клиента есть ответ (`resume` и переподключение). Клиентского кода это не требует:
на `ping` отвечает сам WebSocket, поэтому лечатся и уже выпущенные сборки.

## Вход и личность

Аккаунт живёт под **внутренним `users.id`**, а способы входа — в отдельной
таблице `identities` (`provider` + `provider_uid` → `user_id`). Провайдер нужен
только чтобы доказать, кто ты: после проверки токена дальше по коду ходит один
`userID`, и наружу (клиенту, в `sender_id`, в команды модерации) уходит тоже
только он. Telegram id, Apple `sub` и Google `sub` **из базы не выходят**.

Провайдеров три. Telegram был первым, но App Store отверг сборку с ним одним по
guideline **4.2.3(i)**: вход требовал установки Telegram. Причина глубже, чем
презентация — рекомендованный ревьюером веб-контент внутри приложения у нас и так
был (`ASWebAuthenticationSession`), но `oauth.telegram.org` требует
существующего аккаунта Telegram и подтверждает вход внутри Telegram-клиента.
Поэтому добавлены Apple (iOS; заодно закрывает 4.8) и Google (Android, где кнопки
Apple нет). Telegram остался: он привычен аудитории и работает там, где нет
сервисов Google.

Что важно в реализации (`oidc.go`, `store.go`):

- **Имя провайдер задаёт один раз** — при регистрации, пока оно пустое; дальше не
  трогает ни вход, ни привязка. Отдельный флаг «задано вручную» не нужен: непустое
  имя и есть признак, что оно уже чьё-то. Иначе человек, введший имя на экране
  онбординга, терял бы его при следующем входе через Telegram. Плата: смена имени
  в Telegram в Эфир не приезжает. Аватар под правило не попадает — обновляется с
  каждым входом, потому что своего аватара у нас завести нельзя.
- **Пустые имя/аватар не затирают сохранённые.** Apple отдаёт имя только при
  первой авторизации и не в токене (клиент присылает его полем `name`), а фото не
  отдаёт никогда — иначе второй вход обнулил бы профиль. Если имя так и не
  доехало, аккаунт остаётся безымянным, и починить это можно только спросив
  человека — для этого есть `POST /profile/name`, а клиент показывает экран ввода
  имени в онбординге, увидев пустое `name`.
- **`@username` трогается только при входе через Telegram**: там пустое значение
  законно (человек снял username), а при входе через Apple оно должно остаться
  как было.
- **Один UID у разных провайдеров — разные люди**: ключ в `identities`
  составной, `google:777` и `telegram:777` не склеиваются.
- **Несколько личностей на аккаунт** — это `POST /profile/link/<провайдер>`
  (кнопка «Привязать Telegram» в профиле клиента). Привязка дозаполняет пустые
  имя и аватар, `@username` обновляет всегда. Слияния аккаунтов нет: занятая
  другим аккаунтом личность отбивается `409 identity_taken`, а наказанная —
  `403`, иначе бан мгновенно переехал бы на привязывающий аккаунт.

Выпилить любого провайдера — убрать кнопку в клиенте и поле в конфиге: дальше
`oidc.go` он не проникает.

## Сообщения

Сообщения живут **7 дней** (`messageTTL`, уборка в `cleanup.go`): гео-чат живой,
неделя истории даёт разговор, а база не растёт бесконечно. Отправка — только
`POST /messages` (`publish.go`): проверка бана, лимит частоты, запись, рассылка
через хаб и пуши. `client_msg_id` делает повтор после обрыва идемпотентным.

**Лимит частоты — по охвату, а не по уровню** (`ratelimit.go`). Токен-бакет на
аккаунт, состояние в памяти (защита от потока «здесь и сейчас», переживать
рестарт ей незачем), а бакетов четыре: район с кварталом, город с областью,
страна и Земля. Реплика на весь мир стоит дороже любой локальной, поэтому считать
их одним счётчиком нельзя — иначе одно сообщение в Землю на час затыкало бы
человека в его же дворе. Свежий аккаунт получает тир жёстче: возраст важнее
репутации, заслуженный темп достаётся тому, кто уже побыл в чате.

**Голоса** (`POST /vote`, `±1` или `0` — снять) складываются в `rating` под
сообщением; `my_vote` показывает клиенту, нажата ли своя кнопка (свой плюс мог
быть погашен чужим минусом). Запас — **10 голосов на всех авторов сразу**, и
тратит его только новый голос: смена знака идёт по занятому слоту, снятие слот
освобождает. Запас восстанавливается по мере того, как отмеченные сообщения
уезжают по TTL, — остаток приезжает клиенту в `votes_left`.

Единственное, на что рейтинг влияет, — **темп автора**: плюсы разгоняют широкие
полосы, минусы тормозят везде. Минусовое сообщение не прячется: лента живая, по
сокету оно ушло мгновенно, и скрытие подействовало бы лишь на тех, кто откроет
историю позже. Бинарного права писать в Землю нет и не будет — гейт это джекпот,
который выгодно накрутить один раз, а непрерывная шкала такого приза не даёт.

**Своё сообщение автор удаляет сам** — `DELETE /messages/{id}`. Метод
идемпотентен: строки уже нет (уехала по TTL, снял модератор, повтор запроса) —
всё равно `200`, чужое — `403`. Голоса уносит каскад, и проголосовавшие получают
свой запас обратно. Жалобы, наоборот, остаются: в них лежит копия текста, иначе
автор стирал бы улику против себя. Удаление доходит до открытых лент кадром
`removed`.

## Модерация

Жалоба на сообщение (`POST /report`) приходит постом в служебный Telegram-канал,
и **реакция происходит там же** — командой в ответ. Авторизация бесплатная:
команды принимаются только из настроенного `telegram_notify_chat_id`, а писать в
канал могут лишь его администраторы, так что своих токенов и паролей вводить не
нужно.

| Команда | Что делает |
|---|---|
| `/ban <id> [причина]` | **мьют на сутки**: читать и заходить можно, отправка закрыта |
| `/block <id> [причина]` | **заблокировать навсегда** + удалить аккаунт со всеми сообщениями |
| `/unban <id>` | снять наказание (счётчик нарушений сохраняется) |
| `/del <msg_id>` | удалить одно сообщение |
| `/purge <id>` | удалить все сообщения пользователя |
| `/help` | список команд |

`id` здесь — **внутренний** id аккаунта (он же в посте жалобы). Telegram id
модератор не видит: наружу он не уходит вовсе.

Удаление доходит до **открытых лент сразу**: `/del`, `/purge` и `/block`
рассылают всем подключённым кадр `removed` (см. `hub.announce`), и клиент убирает
контент из ленты. Без этого сообщение оставалось бы на экранах до перезапуска
приложения — в БД его уже нет, но историю клиент не перезапрашивает.

### Блокировка другого пользователя

Модератор нужен не всегда: `POST /block` (и `{"unblock": true}` обратно) прячет
от человека всё, что пишет другой, `GET /blocked` отдаёт список с профилями для
экрана «Заблокированные». Требование Apple 1.2 — в приложении с UGC должен быть
такой механизм.

Фильтр разложен по трём местам, и это не дубль: **историю** сервер отдаёт уже без
заблокированных, **живую рассылку** отсекает клиент по списку id, который
приезжает в ответе про личность (`blocked`), **пуши** отсекает `PushTargets`.
Рассылать в сокет по-разному каждому подписчику хаб не умеет и учить его этому
дороже, чем отдать клиенту список из десятка чисел.

Блокировка односторонняя и наказанием не является: заблокированный ничего не
узнаёт, продолжает писать другим, счётчик нарушений не растёт. Но пост в
служебный канал уходит — этого тоже требует Apple 1.2, и это сигнал о проблемном
человеке даже без жалобы (в горутине: ответ клиенту не ждёт Telegram).

**Автоматической эскалации нет** — решает модератор. В посте жалобы видно,
сколько раз автора уже наказывали («первая жалоба на этого автора» или «наказаний
ранее: N»), и там же готовые команды с подставленными id. Причина необязательна,
но если указана — пользователь её увидит в сообщении об отказе.

Ключевое решение: таблица `bans` живёт **отдельно от `users` и без FK**, а ключ —
**личность у провайдера** (`provider` + `provider_uid`), а не внутренний id.
Причина: удаление аккаунта уносит и `users`, и его `identities`, а вход происходит
по личности у провайдера — значит только на неё наказание и можно надёжно
повесить. Иначе нарушитель удалил бы аккаунт, вошёл тем же Apple ID и получил
чистый профиль. Поэтому же вход проверяется **до** создания аккаунта
(`BanStatusForIdentity`), а наказание пишется сразу на **все** способы входа
человека — иначе его обошли бы сменой кнопки на экране входа.

`bans.user_id` — копия на момент наказания (без FK): по ней работают команды
модератора после удаления аккаунта. А `BanCount`/`Unban` ищут и по `user_id`, и
через `identities`, потому что вернувшийся после `/block` получает **новый**
внутренний id — иначе рецидивист выглядел бы новичком, а `/unban` по новому id
промахивался.

Временный бан истекает сам (сравнение `until` со временем), фоновой уборки нет.

Временный бан — это **мьют, а не выселение**: сессии не отзываются, сокет не
рвётся, человек продолжает читать — отбивается только отправка
(`403 banned` на `POST /messages`, клиент показывает причину и возвращает текст
в поле ввода).
Сессии уходят лишь вместе с аккаунтом, то есть при постоянном бане (каскадом от
`DeleteUser`), и только он запрещает вход (`403 banned`) и апгрейд сокета — иначе
нарушитель зарегистрировался бы заново тем же Apple ID / Telegram. Текст
пользователю один на все точки — `BanMessage`, с остатком времени.

При старте сервер **подтверждает накопившиеся обновления, не исполняя их**
(`skipBacklog`): иначе рестарт повторил бы старые команды, а `/ban` не
идемпотентен — второй раз он означает «повторное нарушение».

## Пуши

Уведомления о новых сообщениях — FCM, **адресно по токенам устройств**. Топики
FCM (топик = канал) выброшены: в топик нельзя *не* отправить конкретному
подписчику, из-за чего автор получал уведомление о своём же сообщении, а fan-out
по топику давал задержку в минуты на Android.

Что где лежит:

| Таблица | Что хранит | Когда меняется |
|---|---|---|
| `device_tokens` | FCM-токен устройства → аккаунт. Ключ — сам токен: при переустановке FCM отдаёт тот же токен, и он должен «переехать» к новому аккаунту, а не задвоиться | `POST /push/register` (вход в чат), `POST /push/unregister` (выход) |
| `user_channels` | набор каналов пользователя — по нему считаются получатели, когда сокета уже нет | на каждый `locate`, **полной заменой** набора |

Отправка: на каждое опубликованное сообщение сервер берёт устройства всех, у кого
этот канал в наборе, **кроме автора и тех, кто автора заблокировал**
(`Store.PushTargets`), и шлёт каждому отдельным запросом (в FCM HTTP v1
мультикаста нет). В заголовке уведомления — имя канала, а `channel` и
`channel_name` едут в `data`, чтобы клиент по тапу открыл нужную ленту (имя
берётся из справочника, который заполняется на `locate`). Ответ
`UNREGISTERED`/404 — приложение удалили или отозвали разрешение: токен удаляется
из БД. Уровни каналов не фильтруются —
подписка на все каналы своей цепочки (пока пользователей мало).

Пуши опциональны: без `fcm_credentials_file` в конфиге `Pusher == nil`, и
отправка работает как раньше, просто без уведомлений.

### Жизненный цикл подписки

- **отписки «от канала» как отдельного действия нет** — набор перезаписывается на
  `locate` целиком: уехал из района, он исчез из набора, пуши оттуда прекратились;
- `locate` приходит, пока приложение живо: вход в чат, реконнект (в т.ч. возврат
  из фона), авто-трекинг (раз в минуту при сдвиге >200 м), ручной выбор точки;
- **смахнули приложение** — WS умирает и живая рассылка в сокет прекращается, но
  `device_tokens` и `user_channels` остаются: пуши продолжают приходить по
  последнему набору каналов. Ради этого они и существуют, отписки при закрытии
  нет и быть не должно;
- полностью устройство отписывается только при выходе/удалении аккаунта
  (`/push/unregister`, у удаления — каскад по FK) либо когда FCM признал токен
  мёртвым.

Известные ограничения:

- **уехал и не открывал приложение** — на сервере лежит старый набор, и пуши из
  покинутого района идут неограниченно долго (лечится порогом по `updated_at` в
  `PushTargets` — поле уже есть, условие не добавлено);
- **один аккаунт на нескольких устройствах** — набор каналов хранится на
  пользователя, а не на устройство, поэтому последний `locate` перетирает его для
  всех устройств аккаунта;
- агрессивные Android-прошивки после смахивания могут не доставлять пуши вовсе —
  вне нашей логики.

## Быстрая проверка

С [`websocat`](https://github.com/vi/websocat):

```sh
go run .                                   # в одном терминале
websocat ws://localhost:8080/ws            # в другом
```

Затем в сессии `websocat` по строке:

```json
{"type":"locate","data":{"lat":55.76,"lng":37.61}}
```

На `locate` сервер ответит `located` с набором каналов (геокодинг через публичный
Nominatim занимает ~2–3 с). Отправка — не кадром, а запросом:

```sh
curl -X POST localhost:8080/messages \
  -H 'Authorization: Bearer <токен сессии>' \
  -d '{"channel":"relation/2555133","text":"привет"}'
```

Токен берётся из ответа `POST /auth/telegram` (нужен реальный вход через клиент)
или заводится напрямую в БД для отладки. Опубликованное разошлётся кадром
`message` всем подписчикам канала, включая автора, — сокету для этого достаточно
`locate`.

## Статус

Приложение опубликовано в App Store и Google Play. Работает: геокодинг
(`NominatimGeocoder`) с кешем и подписями единиц, вход через Telegram / Apple /
Google (проверка ID-token по JWKS, аккаунт под внутренним id, привязка нескольких
личностей), персистентные аккаунты, сессии и сообщения (SQLite; сообщения живут
7 дней), подписка и рассылка сквозь хаб с keepalive, логаут и удаление аккаунта,
жалобы и команды модерации в служебном Telegram-канале, блокировка пользователя
пользователем, голоса под сообщениями и удаление своего сообщения, rate limiting
по охвату канала и репутации, пуши о новых сообщениях (FCM, адресно), счётчик
подписчиков канала, проверка версии клиента (`GET /version`), еженедельная сводка
в служебный канал. Не реализовано:

- **Переподписка диффом** — при смене единиц соединение переподписывается
  целиком, а не только на изменившиеся уровни.
- **TTL сессий** — токены живут бессрочно, отзываются только логаутом.
- **Свой Nominatim** — публичный сервер ограничен 1 req/s (запросы
  сериализуются) и вдобавок **не гарантирует однозначность**: цепочка родителей
  зависит от того, какой вариант кеша ответит (см. TODO в `ether-meta/README.md`).
  Для production нужен свой инстанс (`nominatim_url` в конфиге).

Зависимости: [`gorilla/websocket`](https://github.com/gorilla/websocket). Go 1.26.
