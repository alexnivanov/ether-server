> Язык — **Go**. Приложение опубликовано в App Store и Google Play: в проде живые
> аккаунты и сообщения, поэтому схема БД меняется только миграцией (см. ниже), а

> [`ether-meta/PROTOCOL.md`](../ether-meta/PROTOCOL.md).

## Роль

Сервер **сам геокодит** — вся логика «координаты → каналы» живёт здесь (в
`ether-research` она прототипировалась на JS и переезжает сюда). Он принимает
координаты пользователя и вычисляет набор **ID каналов** (формат — контракт в
parent: ISO 3166-1/-2 для страны/области, `osm_type/osm_id` для
города/района/квартала). Сервер:

- геокодит координаты в набор ID каналов;
- хранит сообщения, ключ = ID канала (админ-ключ);
- держит WebSocket-соединения и рассылает сообщения подписчикам канала;
- управляет подпиской: при коннекте — на текущий набор каналов; при движении
  пользователя — переподписка только на изменившиеся уровни;
- отдаёт REST (`rest.go`) там, где не нужен пуш/сокет как объект: проверка и
  восстановление сессии, согласие с правилами, история сообщений.

Внутри хранения и рассылки канал — это просто **строка-ключ**, но саму эту строку
из координат вычисляет сервер.

## Контракт с клиентом

Клиент шлёт серверу свои координаты; сервер через геокодинг вычисляет набор ID
каналов для точки. Важное следствие однозначности из parent: два клиента в одном
месте дают одинаковые ID → попадают в один чат.

## Как устроено (заметки)

- **Вход** — провайдеров три: Telegram, Apple, Google. Нативный SDK на клиенте
  отдаёт OIDC ID-token (JWT); сервер проверяет подпись по публичным ключам
  провайдера (JWKS) и клеймы (`POST /auth/<провайдер>`, `oidc.go`). Секретов
  провайдеров серверу не нужно, сети к ним нет (JWKS тянется лениво). Аккаунт
  живёт под внутренним `users.id`, способы входа — в таблице `identities`
  (`provider` + `provider_uid`), и наружу уходит только внутренний id. Гостевого
  режима нет — отправка только с валидной сессией.
- **Сессии** — токен в SQLite (`store.go`), выдаётся в ответе `/auth/<провайдер>`;
  повторный вход — `POST /session/resume`, логаут — `POST /session/logout`
  (идемпотентно, один токен). WS сам authed через `?token=` при апгрейде
  (`wsHandler`), отдельного кадра входа нет. TTL токенов пока нет.
- **Согласие с правилами** — `users.rules_accepted_at`, привязано к аккаунту
  (`POST /rules/accept`); в ответе про личность — поле `rules_accepted`. Версий
  правил нет — понадобится `rules_version`, если текст изменится.
- **Сообщения** — таблица `messages` хранит только `user_id` автора (не имя);
  имя (`full_name`) и `avatar_url` для отдачи клиенту берутся `JOIN` из `users` (история) или
  из авторского соединения (live). Так фото/имя всегда актуальны, без дублей в
  каждой строке.
- **Метод — в паттерне маршрута** (`"POST /messages"`, `rest.go`): проверок
  метода в хендлерах нет, `405` с заголовком `Allow` отдаёт сам `ServeMux`.
  Ответ на неверный метод при этом текстовый, а не JSON — единственное такое
  место, и происходит оно только при ошибке клиента. `"GET /path"` ловит и `HEAD`
  (важно для `/app`: по нему ходят сборщики превью ссылок).
- **Токен сессии — только в заголовке** `Authorization: Bearer` (`bearerToken`
  и `sessionUser` в `rest.go`): одна точка проверки вместо одиннадцати повторов
  и токен не попадает в URL. Прежние места (поле `token` в теле, `?token=` в
  query) сняты вместе с поддержкой сборок ≤1.3.0. WS остался на `?token=` — это
  handshake, заголовков в апгрейде нет; это исключение навсегда. Не-Bearer
  заголовок считается отсутствием токена (400), а не мусорным токеном (401):
  чужой `Authorization` от прокси не должен выкидывать человека на онбординг.
- **Keepalive сокета** (`client.go`) — сервер сам пингует каждое соединение
  (`pingPeriod` 50 с) и требует ответа в срок (`pongWait` 60 с, дедлайн чтения
  сдвигает и pong, и любой кадр клиента). Зачем: в протоколе тишина — норма
  (человек читает, писать нечего), а оператор/NAT роняет простаивающий TCP через
  ~30–120 с, и без пингов этого не замечает ни одна сторона: сокет становится
  зомби — сообщения не идут, ошибки нет, подписка в хабе жива и рассылка уходит в
  никуда. Пинг и держит канал живым, и превращает мёртвое соединение в честный
  обрыв, на который у клиента есть ответ (переподключение через `resume`).
  Лечит **и уже выпущенные сборки**: на ping отвечает сам WebSocket (`dart:io`,
  браузер), клиентского кода это не требует. Отсюда же `writePump` на `select` с
  тикером вместо `range` по очереди — писатель в сокет должен быть один, значит
  и пинги идут через него. Периоды — поля `Client`, а не глобальные переменные:
  тест держит их в миллисекундах вместо минут, а помпы читают их из своих
  горутин и переживают конец теста (`httptest` не ждёт hijacked-соединений) —
  подмена глобальной переменной была бы гонкой, и `-race` её ловил. Каждая
  половина keepalive закреплена своим тестом (`keepalive_test.go`), оба проверены
  на падение без неё.
- **REST vs WS** — resume/logout/accept_rules, вход, **чтение и отправка
  сообщений** (`GET`/`POST /messages`) живут в REST (`rest.go`): это синхронный
  запрос-ответ без побочных эффектов на сокете. На WS осознанно остались `locate`
  (настройка конкретного соединения) и `message` (рассылка). Токен сессии —
  только заголовком `Authorization: Bearer`; единственное исключение и навсегда —
  `?token=` при апгрейде WS, заголовков в апгрейде нет.
- **Подпись канала — тип единицы, а не имя слота** (`unit_title.go`): `level`
  про охват (иконка, порядок, полоса лимита), `label` про сам объект, и в
  сельской местности они расходятся — в слот «Город» ложится муниципальный
  округ, в «Район» деревня. Слово выводится из данных OSM: тип `place=*` по
  словарю либо типовое слово в начале имени админединицы (тогда оно уезжает из
  `name` в `label`); не распозналось — остаётся подпись слота. Клиент печатает
  `label` как есть, своих названий уровней у него нет, поэтому правка чисто
  серверная. Тот же словарь — в прототипе `ether-research`, они обязаны
  совпадать.
- **Пробелы словаря подписей копятся сами** (`unmapped_unit`, строка «🏷 Без
  подписи, всего» в недельной сводке): туда идёт не всякий откат на подпись
  слота, а только похожий на пробел — незнакомый тип `place=*` либо типовое
  слово в КОНЦЕ имени, не совпадающее с подписью слота («Клинский район» в слоте
  Города). Иначе список состоял бы из «Москвы» и «Тверского», где чинить нечего.
  Строка — на уникальную единицу, `seen` считает промахи геокеша, а не людей.
  Чистка не ручная: строки помнят отпечаток словаря (`unitDictHash`), и при
  старте сервер выносит снятые прежним — правка словаря и есть сброс списка.
- **Схема БД — по номерам версий** (`store.go`): `PRAGMA user_version` в самой
  базе, шаги в `migrations`, каждый ровно один раз и в транзакции с повышением
  номера. Изменение = актуальный вид в `storeSchema` + шаг + поднять
  `schemaVersion`. Шаги применяются ДО `storeSchema`: схема описывает конечный вид
  и может ссылаться на колонки, которых в дожившей базе ещё нет.
- **Отправка сообщений** (`publish.go`) — только `POST /messages`: проверка
  бана, лимит частоты, запись, рассылка и пуши. Транспортов было два (ещё кадр
  `publish` на WS), и общая функция держала их проверки едиными; кадр снят, а
  разделение осталось — оно держит границу между разбором HTTP и тем, что значит
  «опубликовать». Лимитер один на процесс (`main.go`), потому что лимит на
  аккаунт, а не на соединение. `client_msg_id` делает повтор идемпотентным.
  Литерал `publish` остался в одном месте — `typePublishGone` в `client.go`:
  кадр отбивается кодом `upgrade_required` с текстом «Обнови Эфир», иначе
  сборка ≤1.3.0 увидела бы техническое `unknown_type`.
- **Версия клиента** (`version.go`) — `GET /version` отвечает, пора ли
  обновляться: пороги по платформам в конфиге (`client_versions`), мягкое
  предложение включается через неделю после даты выхода версии. Версия НЕ ездит
  с каждым запросом заголовком и серверной страховки (отказ старым сборкам) нет —
  вердикт уважает клиент. Отметки о версиях (`client_version`) попадают в
  еженедельную сводку — по ним и решается, когда снимать старые способы работы.
