## Роль

Сервер **сам геокодит** — вся логика «координаты → каналы» живёт здесь (в
`ether-research` она прототипировалась на JS и переезжает сюда). Он принимает
координаты пользователя и вычисляет набор **ID каналов** (формат — контракт в
parent: ISO 3166-1/-2 для страны/области, `osm_type/osm_id` для
города/района/квартала). Сервер:

- геокодит координаты в набор ID каналов;
- хранит сообщения, ключ = ID канала (админ-ключ);
- держит WebSocket-соединения и рассылает сообщения подписчикам канала;
- управляет подпиской: при коннекте — на текущий набор каналов; при движении
  пользователя — переподписка только на изменившиеся уровни;
- отдаёт REST (`rest.go`) там, где не нужен пуш/сокет как объект: проверка и
  восстановление сессии, согласие с правилами, история сообщений.

Внутри хранения и рассылки канал — это просто **строка-ключ**, но саму эту строку
из координат вычисляет сервер.

## Контракт с клиентом

Клиент шлёт серверу свои координаты; сервер через геокодинг вычисляет набор ID
каналов для точки. Важное следствие однозначности из parent: два клиента в одном
месте дают одинаковые ID → попадают в один чат.

## Как устроено (заметки)

- **Вход** — нативный Telegram Login SDK на клиенте отдаёт OIDC ID-token (JWT);
  сервер проверяет его подпись по публичным ключам Telegram (JWKS) и клеймы
  (`POST /auth/telegram`, `telegram.go`). Секретный токен бота серверу не нужен;
  сети к Telegram нет (JWKS тянется лениво). Гостевого режима нет — `publish`
  только на authed-сокете.
- **Сессии** — токен в SQLite (`store.go`), выдаётся в ответе `/auth/telegram`;
  повторный вход — `POST /session/resume`, логаут — `POST /session/logout`
  (идемпотентно, один токен). WS сам authed через `?token=` при апгрейде
  (`wsHandler`), отдельного кадра входа нет. TTL токенов пока нет.
- **Согласие с правилами** — `users.rules_accepted_at`, привязано к аккаунту
  (`POST /rules/accept`); в ответе про личность — поле `rules_accepted`. Версий
  правил нет — понадобится `rules_version`, если текст изменится.
- **Сообщения** — таблица `messages` хранит только `tg_id` автора (не имя);
  имя (`full_name`) и `avatar_url` для отдачи клиенту берутся `JOIN` из `users` (история) или
  из авторского соединения (live). Так фото/имя всегда актуальны, без дублей в
  каждой строке.
- **Метод — в паттерне маршрута** (`"POST /messages"`, `rest.go`): проверок
  метода в хендлерах нет, `405` с заголовком `Allow` отдаёт сам `ServeMux`.
  Ответ на неверный метод при этом текстовый, а не JSON — единственное такое
  место, и происходит оно только при ошибке клиента. `"GET /path"` ловит и `HEAD`
  (важно для `/app`: по нему ходят сборщики превью ссылок).
- **Токен сессии — в заголовке** `Authorization: Bearer` (`sessionUser` в
  `rest.go`): одна точка проверки вместо одиннадцати повторов и токен больше не
  попадает в URL. Прежние места (поле `token` в теле, `?token=` в query) сервер
  принимает ради сборок ≤1.3.0; заголовок главнее, если пришли оба. WS остался на
  `?token=` — это handshake, и заголовки там умеет не всякий клиент.
- **REST vs WS** — resume/logout/accept_rules, вход, **чтение и отправка
  сообщений** (`GET`/`POST /messages`; `GET /history` — прежнее имя чтения,
  осталось ради сборок ≤1.3.0) живут в REST (`rest.go`): это синхронный
  запрос-ответ без побочных эффектов на сокете. На WS осознанно остались `locate`
  (настройка конкретного соединения) и `message` (рассылка).
- **Схема БД — по номерам версий** (`store.go`): `PRAGMA user_version` в самой
  базе, шаги в `migrations`, каждый ровно один раз и в транзакции с повышением
  номера. Изменение = актуальный вид в `storeSchema` + шаг + поднять
  `schemaVersion`. Шаги применяются ДО `storeSchema`: схема описывает конечный вид
  и может ссылаться на колонки, которых в дожившей базе ещё нет.
- **Отправка сообщений** (`publish.go`) — один путь на два транспорта: `POST
  /messages` и устаревший кадр `publish`. Проверки бана и частоты, запись,
  рассылка и пуши общие — иначе через один транспорт оказалось бы можно то, что
  через другой нельзя. Лимитер поэтому один на процесс и на оба транспорта
  (`main.go`), иначе лимит обходился бы чередованием. `client_msg_id` делает
  повтор REST-отправки идемпотентным; кадром он не передаётся. Учёта, каким
  транспортом пришло сообщение, сознательно НЕТ: пользователей мало, и когда
  снимать кадр — решение человека, а не метрики (см. `ether-meta/PLANS.md`,
  шаг 3).
- **Версия клиента** (`version.go`) — `GET /version` отвечает, пора ли
  обновляться: пороги по платформам в конфиге (`client_versions`), мягкое
  предложение включается через неделю после даты выхода версии. Версия НЕ ездит
  с каждым запросом заголовком и серверной страховки (отказ старым сборкам) нет —
  вердикт уважает клиент; отброшенный вариант с `426` описан в
  `ether-meta/PLANS.md`. Отметки о версиях (`client_version`) попадают в
  еженедельную сводку — по ним и решается, когда снимать старые способы работы.
